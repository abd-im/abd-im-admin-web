# ABD IM 管理后台重建计划

更新日期：2026-09-08

状态：应用开发已完成，保留原管理功能并新增版本管理；上线前的隔离环境写入验收和服务器下载配置尚待完成。详见 [验收记录](verification.md) 和 [架构与国际化规范](architecture.md)。

## 1. 目标与边界

在 `abd-im-admin-web` 中独立实现 React 管理后台，替代现有闭源 OpenIM-Admin 前端。复用现有 ABD IM 后端，保留原后台的页面、查询条件、数据字段、操作和操作结果，并增加应用版本管理。

- **原有管理功能不能丢失**。验收单位是完整操作流程，保留同名菜单不代表完成。
- 界面与 `abd-im-web` 统一，采用现有 OKLCH 设计 Token、紧凑布局和浅色/深色主题。
- 优先完成旧功能对等，再接入新增版本管理；阶段性交付不视为替换完成。
- 本次重建前端，不重写认证、业务数据库、IM 服务或文件存储服务。
- 不预先增加原后台没有要求的权限平台、插件系统、低代码表单引擎等能力。
- 原后台用于读取和核对。写操作在隔离测试环境或专用测试数据上验证；浏览原后台时不修改现有用户、群组或发送通知。
- 登录凭据和会话 Token 不写入文档、代码、测试夹具或仓库。

### 核对补充规则

1. 每页记录原路由、查询参数、响应字段、表单默认值、校验规则、行操作及成功后刷新方式。
2. 空列表不能用来判定没有行操作。优先读取原页面加载的客户端行为，并在测试环境补足数据进行验证。
3. 分页、重置、跳页、选择状态、返回列表等公共交互也属于功能对等范围。
4. 可搜索的用户/群组选择器必须保留；仅用手填 ID 文本框替代不算完成。
5. 上传必须真正接入现有存储服务；仅提供 URL 输入框不等价于原头像/附件上传。
6. 消息按实际类型解析和展示。文本、图片、文件等不能统一显示为原始 JSON；未知类型可以保留可查看的原始内容。

## 4. 新增应用版本管理

复用后端 `/application/add_version`、`update_version`、`delete_version`、`page_versions`，对接客户端使用的 `/application/latest_version`。

- 支持平台筛选、版本列表、创建、编辑、删除、更新说明和安装包下载地址。
- 核对 `latest`、`force`、`hot` 的服务端语义和客户端支持情况，再确定界面字段及校验。不能把仅保存标记描述为已实现强制更新或热更新。
- 更新接口使用对应的 `{ value: ... }` 包装字段；删除接口为 `id` 数组。按实际协议测试，不共用错误的通用 CRUD 请求格式。
- 核实多个 `latest` 标记的排序行为，不假定设置新版本会自动取消旧版本标记。
- 桌面端当前按 `windows`、`mac`、`linux` 查询；架构区分能力需与现有客户端核对，不能自行引入客户端无法识别的平台名。
- 当前更新流程是检查版本并打开下载链接。本计划不把它扩展为静默下载安装。

安装包继续存放在服务器，例如：

```text
/var/www/downloads/abd-im/1.0.1/ABD-IM_1.0.1.exe
```

由 Nginx 将下载目录映射为可访问的 HTTP(S) 地址，管理后台保存该地址。首版不增加安装包上传服务；头像和通知附件使用已有对象存储上传能力。

验收：保存测试版本后，客户端通过同一后端查询到正确平台、版本、说明和可下载地址；无新版、无记录、无效链接及请求失败均有对应处理。

## 5. 技术与设计约定

### 技术栈

- React、TypeScript、Vite，使用初始化时已核对的稳定版本。
- React Router 管理路由，TanStack Query 管理请求缓存与写入后的刷新，Axios 请求现有接口。
- Lucide 图标，CSS 语义 Token；Zod 用于确有必要的边界数据校验。
- i18next + react-i18next 管理中英文；类型化翻译键、键/插值一致性与硬编码文案检查纳入自动验证。
- 使用 `pnpm`。依赖在 `package.json` 使用正常的兼容版本范围，提交 `pnpm-lock.yaml` 固定每次实际安装结果；不把所有直接依赖改成精确版本。
- 日常新增依赖使用 `pnpm add` / `pnpm add -D`；CI 和生产构建使用 `pnpm install --frozen-lockfile`。
- 当前依赖清单是起点。无实际用途的依赖不继续增加，升级独立于功能实现进行。

### 界面

- 复用 Web 端的五层 Surface、文本层级、品牌蓝和日夜主题，不另造一套视觉体系。
- 左侧分组导航、顶部当前位置、紧凑筛选栏和数据表格；业务页面不做营销式布局。
- 图标按钮提供名称提示，危险操作明确展示目标和后果；弹窗支持键盘关闭、焦点管理和提交中状态。
- 表格支持横向滚动，窄屏导航和弹窗可用；文字不遮挡控件。
- 区分首次加载、刷新、无数据、查询失败、无权限和会话过期，禁止将失败伪装成空列表。
- 深色主题和语言切换分别验收；先核实原语言范围，再确定翻译覆盖。

### 实现范围

- 按页面和领域组织代码。表格、分页、选择器、上传、确认弹窗按真实复用需求提取。
- 现有通用 `ResourcePage` 只用于简单列表。群成员、消息、通知等复杂流程使用独立页面，避免持续堆叠配置开关。
- 管理接口与 IM 接口使用各自 Token；Chat 接口是否接受管理员 Token 以已核实协议为准。
- 查询缓存键包含服务、资源、筛选、分页及用户上下文；用户消息与群消息不能因为接口路径相同而共用错误结果。
- 秒/毫秒、枚举、嵌套响应及更新包装字段在对应模块显式适配。

## 7. 验证方法

- 对高风险契约写针对性测试：Token 分流、更新包装字段、查询缓存隔离、时间单位、群身份与通知批量结果。
- 使用 Playwright 覆盖登录、选择用户、表单校验、确认/取消、分页筛选、上传失败及重要写操作流程；模拟数据只存在于测试中。
- 对桌面及窄屏截图进行人工检查，覆盖导航、长表格、弹窗和深色主题。
- 真实服务联调区分读取和修改；不使用现有生产用户作为封禁、下线、删除关系、解散或群发的测试对象。
- 每阶段记录构建结果、测试范围和未验证部分，不用“页面能打开”代替功能验收。

## 8. 当前已知缺口与下一步

应用开发、分层、中英文和自动回归已完成，主菜单没有开发占位页面。原监控接口重定向到占位域名，本机通过已验证可访问的 Grafana 地址配置；服务器正式配置需同步修正。给定安装包路径在 IP 对应公网入口返回 404，需要部署提供的 Nginx 下载映射。
